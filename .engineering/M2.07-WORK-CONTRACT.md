## Exact objective

Build the first real Worker assessment-attempt lifecycle on top of M2.05 immutable generated forms and M2.06 backend-authoritative eligibility. A Worker can start an eligible assessment, receive exactly one pinned question, submit a type-valid answer that is durably committed before the next question is revealed, continue safely across reloads using committed state, and submit the final answer into an immutable `SUBMITTED` attempt receipt.

M2.07 owns committed attempt progression only. It does not own uncommitted autosave/recovery, secure-window/proctoring integrity, scoring, pass/fail, reviewer allocation, result publication, retakes, interviews or credentials.

## Data-integrity/security constraints

1. Attempt identity is server-generated and one generated form can belong to at most one attempt.
2. Attempt lineage pins `caseId`, authenticated `workerAccountId`, catalogue version, blueprint version and generated form.
3. Attempt statuses are only `IN_PROGRESS` and `SUBMITTED`.
4. `currentPosition` is 1-based; while in progress it names the current pinned form item. A submitted attempt keeps `currentPosition = questionCount`.
5. One committed answer exists at most once for each `(attemptId, position)`.
6. Answer rows retain composite form/item/question/question-version lineage so cross-form or cross-version substitution fails at the database boundary.
7. Worker identity always comes from the live principal; roles other than Worker cannot operate Worker attempts by id.
8. Begin locks the owned case, re-resolves current M2.06 eligibility, creates/loads the M2.05 form inside the same outer transaction, creates/loads the attempt, changes the case once to `Assessment in progress`, then records timeline/audit evidence.
9. Current-question projection contains only attempt progress plus the single pinned current question and safe metadata.
10. Six canonical question types are supported: `MULTIPLE_CHOICE`, `TRUE_FALSE`, `SHORT_TEXT`, `LONG_TEXT`, `INTEGER`, `DECIMAL`.
11. Type normalization is server authoritative. MCQ must be one pinned option; TRUE_FALSE must be boolean; text must be non-empty and within frozen Unicode code-point limits; INTEGER must be JS-safe; DECIMAL must be finite.
12. Submission locks the owned attempt, validates stale guards against the pinned requested item, normalizes the answer, inserts it once, and only then advances or submits.
13. Identical replay of an already committed immutable answer returns the current authoritative view without double progression. A different replay conflicts.
14. Final submission writes exactly one submit timeline/audit event and does not move the Assurance Case beyond `Assessment in progress`.
15. Audit metadata contains no answer content, correctness or scoring data.
16. M2.07 down migration restores the pre-M2.07 audit action vocabulary without deleting historical M2.07 audit rows; the restored CHECK rejects new M2.07 actions after rollback.

## Mandatory acceptance criteria

1. Migration creates `assessment_attempts` and `assessment_attempt_answers` with strong lineage and typed-value constraints.
2. Down/reapply removes/restores only M2.07-owned schema and restores the prior audit action vocabulary while preserving existing append-only audit history.
3. Begin requires live Worker authorization and ownership; other Worker, revoked Worker and non-Worker fail closed.
4. Begin on an eligible pending case atomically creates one generated form/attempt, transitions the case once to `Assessment in progress`, and returns only question one.
5. Repeated/concurrent begin calls converge on the same attempt/form with no duplicate timeline/audit effects.
6. Forced failure after form generation rolls back form, attempt, case transition, timeline and audit together.
7. All six canonical answer types accept valid normalized values and reject invalid values without progression.
8. MCQ rejects values outside the pinned option set.
9. SHORT_TEXT trims edges, preserves internal content and enforces 2,000 Unicode code points.
10. LONG_TEXT trims edges, preserves internal content and enforces 20,000 Unicode code points.
11. INTEGER rejects fractions and out-of-safe-range values; DECIMAL rejects non-finite values.
12. A committed answer row exists before the next question becomes authoritative.
13. Current-question reads continue to use the pinned historical question version even if the stable question later changes status/version.
14. Parallel identical submissions create one answer and one progression only.
15. Identical stale replay is idempotent; different replay is a conflict.
16. Parallel identical final submissions create one `SUBMITTED` transition, one submit audit and one submit timeline event.
17. Answer-persistence failure rolls back progression and leaves no partial answer.
18. Final submission leaves Assurance Case status `Assessment in progress`; no M2.10 transition or scoring occurs.
19. Worker Available Assessments stays read-only on GET and exposes a real POST start control only for eligible cards.
20. Begin action accepts only case/catalogue authority, derives Worker/form/blueprint server-side and redirects to the created owned attempt.
21. Assessment GET page reads only the authenticated Worker's owned attempt.
22. Submit action accepts only attempt id, position/question-version stale guards and current answer; expected errors map to coarse UI state.
23. Worker assessment workspace renders one current question across all six controls, disables submission while pending, has no Previous control and uses `Submit assessment` on the final item.
24. Real Chromium proves Worker login → available assessment → start → MCQ answer → written answer → refresh committed state → final submitted receipt.
25. Browser HTML and captured response bodies contain no future prompt, answer key, rubric, score/correctness/pass-fail or full-form leakage.
26. Cross-Worker direct attempt URL/operation is denied.
27. Native audit actions are exactly `assessment.attempt.started` and `assessment.attempt.submitted`, with answer-content-safe metadata.
28. Permanent `check:m2-07` and `test:m2-07` commands exist and aggregate Full Engineering executes both M2.07 source-contract and runtime gates.
