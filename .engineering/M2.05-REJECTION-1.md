## Failed mandatory criterion

Once a stable `assessment_questions.question_id` has appeared in a generated form for a Worker, that stable question must never be persisted again for that Worker, including when two different Assurance Cases are generated concurrently.

## Verified evidence

- The committed database-level reproduction creates a valid first form for one Worker and then attempts a second different form/case containing the same stable question for the same Worker.
- The permanent M2.05 aggregate ran the reproduction on exact commit `946ef2d...`.
- Four prior database-integrity invariants passed in that same run.
- The new non-repetition invariant failed with `Missing expected rejection`, proving the database accepted the second Worker/question exposure.
- The form-generation service currently checks prior exposures before insertion, but different case transactions are not serialized by the existing unique `(case_id, blueprint_version_id)` boundary.

## Root cause

Permanent Worker-level exposure history is enforced as a service-side read-before-write rule, but the persistence model lacks a unique database identity for `(worker_account_id, stable question_id)`. Two concurrent transactions for different cases can both observe the question as unseen and both commit it.

## Revision 1 correction boundary

Use `generated_assessment_form_items` as the single exposure-history authority:

1. Persist `worker_account_id` on each generated form item.
2. Derive that Worker identity from the parent `generated_assessment_forms` row inside the database; do not trust the insertion caller.
3. Enforce parent form/Worker consistency.
4. Enforce uniqueness on `(worker_account_id, question_id)`.
5. Preserve existing form/item append-only and completeness guarantees.
6. If a cross-case concurrent generation loses this uniqueness race, return a safe `AssessmentFormGenerationError` rather than exposing raw SQL details.

## Explicitly forbidden fixes

- Removing or weakening the failing test.
- Adding only an in-process mutex/application lock.
- Accepting caller/browser-supplied Worker identity as exposure authority.
- Re-randomizing or silently retrying with a form that could expose a question without preserving the permanent exposure invariant.
- Creating a second independent exposure ledger unless evidence proves generated form items cannot safely own the invariant.

## Gatekeeper state

`REJECTED` pending Revision 1 and rerun of all affected mandatory gates.
