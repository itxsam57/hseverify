- `ASSESS-ELIG-001` — Worker availability derives only from the authenticated Worker and owned Assurance Case.
- `ASSESS-ELIG-002` — Qualification prerequisites count only exact-current submitted qualification versions with terminal approved review lineage.
- `ASSESS-ELIG-003` — Availability reads are side-effect free and must not create forms/attempts or mutate case state.
- `ASSESS-UI-003` — Admin catalogue and Worker available-assessments routes are visible, authorized, and contain no dead attempt-start control.

## Exact objective

Build a versioned Assessment Catalogue and a read-only Worker availability model. Administrators publish immutable catalogue versions that pin an exact M2.05 blueprint version and framework. Workers see only offerings for their own existing `Assessment pending` Assurance Cases when all backend eligibility rules are satisfied, including the case policy framework and the configured count of approved exact-current submitted qualification evidence.

M2.06 decides **availability only**. It does not start, generate, run, answer, score, finish, or retry an assessment attempt.

## Data-integrity/security constraints

1. Stable catalogue identity may point only to a version belonging to that same stable entry.
2. Catalogue version `(framework_id, blueprint_version_id)` must point to an exact M2.05 blueprint version with that framework.
3. Catalogue version rows are append-only and rollback/reapply is history-preserving.
4. Admin create/revise/status mutations require a live, active, unrevoked Admin session.
5. Worker availability requires a live Worker session plus `worker.assessments.read`.
6. Worker identity is always `principal.accountId`.
7. `findAvailableForCase()` scopes ownership before eligibility and returns the same null/empty shape for malformed/missing/copied other-Worker case ids.
8. Case must be `Assessment pending` and have exactly one immutable policy snapshot matching catalogue framework.
9. Stable catalogue and stable blueprint must be ACTIVE.
10. Catalogue pins the exact immutable blueprint version; that version need not still be the blueprint’s current version.
11. Qualification count is `DISTINCT` qualifying current qualification records for the authenticated Worker only.
12. Availability reads mutate no catalogue/evidence/review/case/form/attempt state.

## Verified qualification definition

A qualification counts only when the same exact version satisfies all of these:

- `worker_evidence_records.worker_account_id = principal.accountId`;
- `record_kind = 'qualification'`;
- `worker_evidence_records.current_version_id = evidence_review_tasks.source_version_id`;
- matching `worker_evidence_versions.record_id` and `version_status = 'submitted'`;
- review task belongs to authenticated Worker, evidence kind `qualification`, task status `APPROVED`;
- terminal review decision points to the same exact source version and outcome `APPROVED`.

Count `DISTINCT worker_evidence_records.record_id`.
