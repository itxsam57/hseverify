## 2. Rejection history and corrective revision

### Rejection 1 — `ARCHITECTURE_DEFECT`

Evidence commit: `946ef2d8c4fcd9459645b595143eee6f600ce872`  
Targeted run: `32121964032`

Independent review found that sequential non-repetition was implemented as read-before-write service logic but the database did not prevent two different Assurance Case transactions for the same Worker from persisting the same stable `question_id` concurrently. The committed RED test proved the second exposure was accepted.

### Revision 1 — accepted root-cause correction

The revision kept `generated_assessment_form_items` as the single exposure-history authority and added a database boundary rather than an application-only lock:

- each item stores `worker_account_id` derived by the database from its immutable parent form;
- `(form_id, worker_account_id)` parent consistency is enforced;
- `(worker_account_id, question_id)` is unique;
- callers cannot choose the exposure Worker identity;
- cross-case uniqueness races cannot commit duplicate exposure;
- unmatched `23505` collisions are converted into a safe `AssessmentFormGenerationError` instead of leaking raw SQL details;
- a real two-case race test plus a forced-uniqueness fault-injection test permanently exercise both paths.

Revision budget used: **1 of 3**. No second root-cause revision was required.
